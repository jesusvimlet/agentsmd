# Investigation: making the agent instructions project-agnostic

Investigation date: 2026-10-17

Source baseline: root `AGENTS.md`, version `0.0.6`

Scope: investigation and recommendations only; no instruction changes or configuration mechanisms are implemented here.

## 1. Executive summary

The repository is currently a reusable **opinionated application template**, rather than a project-agnostic knowledge base. Its instructions mix broadly reusable engineering practices with a particular Node.js/Express backend, an entity-oriented application architecture, a browser-native SPA, PostgreSQL-compatible persistence, pnpm, dotenvx, Jest, Puppeteer, Supabase authentication, and Socket.IO.

There is **one literal `AGENTS.md` file**: `AGENTS.md`. Its §0 requires reading all files under `agents/`, so the nine Markdown files there are also part of the effective instruction set and are included in this report. There are no other repository `AGENTS.md` files in the inspected inventory. Several references to layer-specific `AGENTS.md` files describe possible files in consuming projects, not files present here.

Main findings:

1. **A useful generic core already exists.** Explicit authorization for repository writes, keeping secrets out of source and output, explaining dependency additions, preserving established behavior, clear module boundaries, meaningful tests, isolated test data, observable cleanup failures, and separating temporary artifacts from permanent code can largely be retained.
2. **Most architecture instructions are reusable only conditionally.** Thin HTTP adapters, separate business logic and persistence, entity-owned modules, external schemas, SPA navigation, native DOM rendering, and module-prefixed CSS are coherent choices for projects that adopt them. They are not universal requirements for every project.
3. **Some values can become configurable placeholders.** Paths, entry points, tools, runtime versions, operation names, authentication context fields, locale locations, and test commands are candidates. Substituting a value does not generalize an architectural mandate: changing the name of Express does not make Express middleware semantics valid in every framework.
4. **Feature presence is currently over-inferred.** A web frontend is treated as implying a backend, REST, authenticated Socket.IO, and ephemeral presence; the frontend documents additionally assume an existing Supabase session and internationalization system. These capabilities need independent applicability conditions.
5. **Several policies require decisions before generalization.** Examples include the exact Git authorization workflow, one module per entity, database-side behavior prohibitions, partial-update semantics, raw versus normalized database results, application/test environment sharing, and compulsory internationalization.
6. **Instruction interactions need an explicit scope model.** Root defaults, files under `agents/`, layer-specific overrides, and testing rules overlap. The current text does not completely resolve same-directory conflicts, absent components, unknown configuration, or rules that cross their stated filesystem scope.
7. **Unresolved decisions must be operation-scoped.** An unknown database adapter should block database-dependent work, not unrelated frontend styling. A project without a backend should not be required to choose backend settings or install backend dependencies.

Recommended direction: retain technology-independent principles as the common baseline; make architecture and technology rules applicable only when the consuming project adopts them; identify required project decisions at the operation that needs them. Do not silently install, scaffold, or infer missing components to satisfy a knowledge-base document.

### 2.2 Classification legend

Sections frequently contain more than one class. The analysis distinguishes reusable wording from values or policies that need a decision.

| Code | Classification | Meaning and treatment |
| --- | --- | --- |
| **G** | Generic / reusable unchanged | The instruction expresses a reusable principle. It can retain its wording within its stated subject, without requiring the current application's technology or domain. |
| **P** | Project- or policy-specific | A concrete stack, topology, naming scheme, owner workflow, architecture, or implementation contract is mandated. It is not a universal default merely because several projects could share it. |
| **T** | Parameterizable | A concrete value could be replaced by a future project-supplied value after its meaning is agreed. This report lists candidates without inserting live markers into instructions. |
| **C** | Conditional | The instruction applies only when a relevant component, technology, or architectural policy is present and selected. Conditional scoping can allow the instruction itself to remain unchanged. |
| **A** | Ambiguous / decision required | The text leaves behavior, ownership, applicability, precedence, or a required contract unspecified. |
| **D/X** | Dependency / possible conflict | The instruction relies on another decision or may conflict with other instructions or a consuming project's architecture. Cross-document cases are collected in §5. |

“Generic” does not mean that an HTTP, browser, or database instruction applies to projects without those components. Likewise, a coherent architecture decision is not necessarily an error: the issue is presenting it as unconditional guidance.

## 3. Applicability and unresolved decisions

### 3.1 Recommended interpretation for a reusable knowledge base

These are proposed semantics to decide before implementation, not an implemented selection or configuration system.

- **Separate existence, selection, and readiness.** A project may have a frontend without a backend; a backend without persistence; authentication without Supabase; or real-time communication without Socket.IO. The presence of one must not activate all the others.
- **Require both architectural applicability and task relevance.** A database instruction can be applicable to the project while remaining irrelevant to a CSS-only change.
- **Treat absent and unknown differently.** An explicitly absent component makes its instructions inapplicable. An unknown component or setting requires clarification only if the operation depends on it. An unfamiliar directory layout alone is not proof that the component is absent.
- **Resolve only the decisions needed by the operation.** Use established project evidence where available. Missing knowledge-base values must not trigger framework installation, directory creation, provider selection, or a project-wide migration by assumption.
- **Keep blockers local.** Report which edit, command, integration check, or bootstrap step depends on an unresolved decision. Continue independent work and available verification. Do not declare a blocked check to have passed.
- **Re-evaluate at integration boundaries.** A frontend change that also changes an API contract may need backend decisions. A frontend presentation change consuming a known contract usually does not.
- **Scope completion criteria.** A documentation change should not require choosing a database; a backend-only project should not require Puppeteer; and a frontend-only project should not require Express or authentication middleware.

### 3.2 Examples of operation-scoped blocking

| Unresolved decision or absent feature | Work that depends on it | Work that can proceed independently |
| --- | --- | --- |
| Backend framework or server entry point unknown | Creating server middleware, starting the backend, or prescribing backend bootstrap commands. | Frontend-only edits against an established contract; documentation; unrelated styles. |
| No backend in the project | No backend instruction applies. A backend is not a missing prerequisite to be supplied. | Static frontend, library, CLI, or documentation work appropriate to the project. |
| Database engine/client unknown | Database implementation, migrations, transaction mechanics, and database-dependent checks. | Pure business calculations with known interfaces, frontend rendering, and isolated tests that do not need the adapter. |
| Authentication provider/context unknown | New protected operations or changes to session/token handling. | Public UI, unrelated CSS, and operations with an already established identity contract. |
| Socket.IO absent | Socket.IO-specific instructions are inapplicable. | REST-only functionality and non-real-time frontend work. |
| Browser support or build model unknown | Introducing browser APIs, compilation steps, or new frontend architecture. | Edits that stay within the project's existing, known module/build conventions. |
| Functional-test target or fixture environment unknown | Running tests that need that target or create real resources. | Applicable local/static checks and isolated unit tests; preparation of tests against known contracts. |
| Internationalization convention unknown | Adding translation keys or changing locale infrastructure, when internationalization is required. | Unrelated behavior or styling changes that do not introduce user-visible text. |
| Release/version target unknown | A requested version bump or release operation. | Ordinary investigation and implementation without an implied release. |

Unknown backend details may still block a full-stack acceptance check even when a frontend edit can proceed. That is a specific verification dependency, not a blanket prohibition on frontend work.

## 7. Open questions before implementation

### 7.1 Knowledge-base consumption and precedence

1. **How will projects consume this repository?** As copied defaults, selected reference documents, or another explicitly chosen distribution model? Which root do paths refer to: this knowledge base or the consuming project?
2. **What is globally mandatory?** Which rules are owner-wide preferences that should remain opinionated across projects, versus optional architectural guidance? This especially affects Git authorization, exact dependency pins, no unsolicited tooling, and test-infrastructure restrictions.
3. **What resolves precedence?** How do root defaults, `agents/`, nested `AGENTS.md` files, and project-specific choices interact? How are peer conflicts resolved, and what does “all global rules remain applicable” mean after an override?
4. **How should capability applicability be established?** Explicit project decisions, existing repository evidence, or both? How should “absent,” “unknown,” and “selected but not configured” be distinguished without creating a global gate?
5. **Must every library document be read for every task?** The current root says yes for `agents/`. A reusable collection needs a decision about retaining that policy versus reading applicable subject matter; no change is assumed by this report.
6. **What is the required behavior for an unresolved decision?** Confirm that only dependent operations pause, that established project evidence may resolve a value, and that unavailable checks are reported without claiming success.

### 7.2 Workflow, versioning, and tooling

7. **Is the literal `push` cycle intentional for every consumer?** Should staging, committing, pulling, and publishing have separate authorization, and how should existing user changes, upstreams, PRs, hooks, and failures affect that workflow?
8. **What is versioned and when?** SemVer or another scheme; one package or multiple release units; manifest/header source; and one bump per task versus one unpublished bump until push. Does every instruction edit require a bump in a future library?
9. **Which runtime/dependency policies are defaults?** Are Node LTS, pnpm, exact pins, frozen installs, and committed lockfiles optional ecosystem examples or mandatory owner policies? How are resolved versions and module formats established?
10. **How broad is the configuration policy?** Are dotenvx and the two environment files optional? Which values may have non-secret defaults? Does the no-hardcoded-port rule intentionally forbid the bootstrap example's fallback?
11. **Where may temporary artifacts live?** Keep `.opencode/tmp/` as an owner convention or adopt a project-selected location? What ignore/cleanup rules apply, and where do permanent tests belong in other layouts?

### 7.3 Backend, contracts, and persistence

12. **Which backend architectures are supported?** Is entity-owned `endpoint → handler → persistence` merely one available pattern? How are entities distinguished from aggregates, services, workflows, jobs, and the shared socket handler?
13. **What are the actual middleware/authentication contracts?** Required protections, covered routes, execution phases, provider selection, trusted context, sanitizer semantics, and public/provider-callback exceptions need definition. In particular, when are route parameters sanitized?
14. **What is the schema contract?** Dialect/representation, validator API/error/coercion behavior, ownership, initialization, composition/registration rules, and request versus response validation are unspecified.
15. **What is the supported partial-update model?** PATCH versus replacement, null-as-delete versus nullable values, arrays, final-record construction, generated required fields, validation timing, and concurrent writes must be reconciled.
16. **What must persistence return?** An exact adapter result or a normalized application result with all meaningful data/metadata? Which transformations are permitted without violating the no-business-logic rule?
17. **How are cross-entity transactions coordinated?** What contract permits atomicity while preserving the stated main-handler and private-adapter boundaries?
18. **How much database behavior is permitted?** Are cascade/trigger/procedure/RPC bans selected application policy? How do metadata generation, database row-security policies, integrity constraints, migrations, and existing schema behavior fit?

### 7.4 Frontend and optional integrations

19. **Which frontend models are intended?** Is the no-build vanilla SPA one selectable model among static sites, MPAs, SSR, compiled clients, and independently hosted frontends? What target browsers/devices and source-serving topology are required?
20. **Are REST, Socket.IO, Supabase, Desktop clients, and presence independent features?** Which projects actually need each? What are the shared socket handler's ownership and the intended presence durability semantics?
21. **Which UI conventions are selected policy?** Mirrored JS/CSS modules, kebab-case/prefixed classes, native DOM-only rendering, global styling, shared tokens, and responsive support need boundaries. Does “CSS module” mean an ordinary owned stylesheet?
22. **Is localization mandatory or optional?** If selected, what shared API, locale format/path, supported languages, fallback/interpolation/plural behavior, and exceptions for user data or literal locale content apply? How does locale fetching coexist with the API-only `fetch` rule?

### 7.5 Verification and environments

23. **What are the supported test categories and boundaries?** Define unit, in-process integration, persistence integration, public API, browser E2E, and real-time checks as applicable, along with locations and commands. Are pure frontend/shared-library units explicitly allowed?
24. **Who owns application lifecycle and target discovery for functional tests?** How is a reachable application/frontend/API URL provided, and are isolated CI deployments, test-specific settings, or framework harnesses ever permitted?
25. **Which real environments and providers may tests use?** Decide approved data isolation, authentication fixture provisioning, secrets/configuration access, and whether any provider/domain mocks are permitted outside full E2E tests.
26. **What if cleanup is unavailable?** Which deletion/provisioning interfaces are approved, how are immutable/provider resources handled, and what exceptions or retention policy reconcile the no-leftover-data mandate with actual public contracts?
27. **What counts as sufficient task verification?** Clarify proportional checks for behavior changes, existing passing coverage, documentation-only work, environment-blocked checks, and the root's blanket requirement to create/update tests. Clarify required versus optional browser automation.

## 8. Recommendations and investigation boundary

Recommended priorities for a later implementation task:

1. Agree on consumption, precedence, applicability, and operation-scoped unresolved-decision semantics first. These determine how every other instruction is interpreted.
2. Preserve the generic principles identified above, and distinguish owner-wide workflow policies from optional technology/architecture guidance.
3. Make component selection independent: frontend, backend, persistence, authentication, real-time transport, presence, localization, and design systems must not imply one another.
4. Parameterize actual project values only after their meaning and ownership are decided. Keep architectural policies conditional rather than pretending that renaming paths or frameworks is sufficient.
5. Resolve the cross-document contracts in §5, especially partial updates/storage validation, persistence results, transaction boundaries, schema infrastructure, and testing lifecycle/integration categories.
6. Review repeated mandates together so that a later generalization of one document does not leave incompatible unconditional rules in its companions.
7. Keep bootstrap, ignore rules, test commands, and completion checks aligned with selected components. A missing optional value must not become an unrelated project-wide blocker.

This investigation does not choose a new stack, instruction-loading format, configuration mechanism, placeholder syntax, or implementation architecture. Candidate future decisions are documented only in this report. No existing `AGENTS.md`, companion instruction file, or other project file is changed by the investigation.
